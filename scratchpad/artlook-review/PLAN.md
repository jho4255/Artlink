### 0.3 작업 규칙 (이 저장소에서 반복된 사고를 막는 것들)

- **커밋 · 배포는 사용자가 말할 때만.** 계획 승인은 구현 지시가 아니고, 구현 지시는 커밋 지시가 아니다.
- **작업 트리에 미커밋 변경이 많다**(규칙 80~84, 브랜치 `feature/community-editor`). `git stash` · 브랜치 전환 금지(개발 서버가 옛 파일을 물고 남는다 — 규칙 77). 시작 전에 사용자에게 "앞 작업을 먼저 커밋할지" 한 번 물을 것. 답이 없으면 같은 트리에서 **아래 '바꿀 파일'에 적힌 파일만** 고친다.
- 서브에이전트 금지 · 사용자에게 보이는 말은 전부 한국어.
- **사용자가 보는 화면에 설명 문구를 늘리지 말 것.** 문장은 눌렀는데 막혔을 때만.
- 실제 가입자의 작품 · 이름을 목업 · 시안 · 칩에 쓰지 말 것. 데모 그림(`frontend/public/demo-art/`)과 가상 작가(윤서진)만.
- 서버: 프론트 5173 · 백엔드 4000(복제본 `artlink_prod`)이 떠 있다. 복제본에서 **개발자 로그인 버튼은 실제 가입자로 들어갈 수 있다** — 가상 계정만 쓴다: 작가 `intro-sample@artlink.test`(id 676, 작품 9점).
- E2E 는 **데모 DB `artlink` 로만**. `global-setup` 이 DB 를 통째로 지운다. 순서: ① `umask 077; pg_dump -Fc artlink > ~/artlink-backups/artlink-demo-before-artlook-<날짜>.dump` ② 백엔드를 `DATABASE_URL=<로컬 데모 DB artlink 주소 — backend/.env.example 의 형식, Prisma 옵션 없이>`(Prisma 옵션 없이)로 다시 띄운다 ③ E2E ④ `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` + `pg_restore --no-owner` ⑤ 백엔드를 복제본으로 되돌린다. E2E 가 도는 동안 소스를 고치지 말 것.
- ArtLook 은 **React 번들 밖의 정적 페이지**다: `frontend/public/artlook/index.html`(스타일 · 마크업 · 엔진) + `ui.js`(화면) + `scene.js`(장면 엔진) + `view.js`(작가 홈페이지 [벽에 걸어 보기] — **같은 엔진을 쓴다**, 규칙 74).
- 화질 하니스는 주소에 `?preload=all` 을 붙여 연다(안 붙이면 고른 것만 받아 '불러오는 중'이 찍힌다).
- CSS: **좁은 칸 규칙을 먼저, `@media (min-width:860px)` 를 뒤에**(규칙 65 — 순서가 바뀌면 좁은 칸 규칙이 죽는다. 소스 가드가 본다).

### WP1 — 그림자: 네 귀퉁이 그늘을 빼고 변 그림자를 살린다

**왜** — 지금은 모서리 폐색(`cornerAO` 0.18, 반경 = 조각 짧은 변의 13%)이 **액자와 그 옆 벽을 함께** 어둡게 한다. 그래서 빛을 받는 모서리의 벽까지 어두워지고(변은 +1~2% 인데 모서리는 −12%), 줄여 보면 얼룩 네 개로 읽힌다. 변을 따라가는 그림자(`LAYERS`)는 그보다 얇다.

**⚠️ 이 값들은 9월에 사용자 지적("덜어내라", "아무것도 안 한 것처럼 자연스러운가")으로 여러 차례 맞춘 것이다**(규칙 37 · 42 · 44b · 44f). 진하게 만드는 방향은 전부 기각된 적이 있다. 그래서 이 묶음은 **G1 에서 전/후를 보이고 사용자가 고른 뒤에만** 남긴다.

**바꿀 파일** — `frontend/public/artlook/scene.js` 하나.

**구현**

1. 모서리 폐색을 조각 안으로 가둔다. `// ── 코너 폐색` 블록(약 1462~1496행)에서 `ctx.save()` 뒤 · 그라디언트를 칠하기 전에 **앞면 사각형(`box.front`, 여러 점이면 칸마다 `g.q`)으로 클립**한다. 그 파일의 그림자 코드가 쓰는 `path(ctx, quad, …)` 도우미를 그대로 쓴다. 이렇게 하면 규칙 42 의 근거(살의 양 끝이 어둡다 — 마이터 이음매)는 남고 벽의 얼룩만 사라진다.
   - 원형 액자는 원래 모서리 폐색이 없다(`u.round`). 그대로.
   - 대안(B): `cornerAO` 기본값을 0 으로. G1 시트에 (A 클립) · (B 0) 를 나란히 넣어 사용자가 고르게 한다. **리뷰 때 뽑은 '고친 뒤'는 B + 그림자 1.5배였다**(목업 맨 위 판).
2. 변 그림자를 올린다. `LAYERS`(약 1336행)의 알파를 1.5배: `cast 0.060 → 0.090`, `contact 0.195 → 0.29`. 블러 · 오프셋은 그대로(규칙 44b — 블러가 오프셋보다 커지면 헤일로다). 후보로 1.3배도 뽑아 시트에 넣는다.
   - 장면마다 `scene.shadow`(0.85~1.08)가 곱해진다. 그건 그대로 둔다.
   - 여러 점은 칸 전부를 한 경로로 한 번 칠한다(규칙 75) — 그 구조를 바꾸지 말 것.
3. `after.mjs ao` 가 덮어쓰는 방식(`{cornerAO:0, shadow:1.5}`)과 실제로 고친 코드의 결과가 같은지 한 케이스로 대조한다(픽셀 차이 평균 1/255 이하).

**함정**

- 어두운 벽(차콜 등)은 절대 낙차가 구조적으로 작다. **통과시키려고 더 진하게 만들지 말 것**(규칙 44k).
- 캔버스 랩은 옆면이 있다(`depth`). 클립 경로는 앞면이다 — 옆면 쪽에 폐색이 남는지 눈으로 볼 것.
- 이 변경은 `view.js`(작가 홈페이지 [벽에 걸어 보기])의 그림도 바꾼다. 액자 칩(`frames/chips`)은 장면 없이 굽는 것이라 안 바뀐다.

**완료 기준**

| 재는 것 | 방법 | 기준 |
|---|---|---|
| 벽의 모서리 그늘 | `shadow.cjs` 의 '모서리 %' — 고친 렌더 ↔ `cornerAO:0` 로 덮어쓴 렌더 | 네 모서리 모두 차이 **1%p 이내** |
| 변 그림자 | `shadow.cjs` '변 중앙 %' 의 0.3~1% 구간, 그늘 쪽 변, 밝은 벽 4종 | **−12 ~ −20%**(지금 −8~−14) |
| 빛 받는 변 | 같은 표 | **0 ± 3%**(그림자가 생기면 안 된다) |
| 작품은 그대로 | `geo` 의 작품 사각형 안쪽 픽셀 ↔ 기준선 | 평균 차이 0 |
| 화질 지표 | `scratchpad/vt`: `run.py --vs base-1117` · `physics.py` · `syncheck.py` · `artpreserve.py` | 통과 수가 기준선보다 줄지 않는다. `contact_drop` 은 밝은 벽에서 20~85 밴드 안 |
| 벽 보기 | e2e `74-wall-view.spec.ts` | 통과 |

### WP2 — 실내 배경 저장본 해상도

**왜** — 실내 사진 7장만 1254px 이다(벽 배경은 1254px 원본을 2배로 늘려 넣어 왔다 — 규칙 44k · 75). 출력 긴 변 = `원본 긴 변 / SCENE_HEADROOM(1.6)` 이라 실내는 하한 1080 에 걸리고, 9:16 은 608×1080 이 된다.

**바꿀 파일** — `frontend/public/artlook/walls/wall11…17-*.jpg`(7장) · `scenes/scenes.json` · `index.html`(`compose()` 의 출력 크기 계산부 약 3055~3062행 + `composeScene` 호출부의 `maxSrcScale`).

**구현**

1. 사진 7장을 **2배**(2508×2508)로 Lanczos 로 늘려 같은 이름으로 덮어쓴다(`sharp` 는 `backend/node_modules/sharp`). 벽 배경 6장을 넣을 때와 같은 방식 · 같은 크기다(규칙 44k) — 그래서 GPU 텍스처 부담도 지금 벽과 같다. JPEG 품질 86 부터 시작해 **장당 900KB 를 넘으면 낮춘다**(실내 사진은 매끈해 잘 줄어든다). 원본은 git 에 있으니 따로 보관하지 않는다. `walls/thumbs/` 는 그대로.
2. `scenes.json` 의 그 7개 장면에 `"srcScale": 2` 를 적는다(뜻: "이 파일은 원본을 이만큼 늘린 것"). `_readme` 에도 한 줄.
3. `compose()` 의 출력 크기 계산을 이렇게 바꾼다(늘려 넣은 사진은 `원본/1.6` 규칙을 타지 않는다 — 그 규칙은 '진짜 픽셀을 넘겨 늘리지 않는다'는 뜻인데 이 파일은 이미 늘린 것이다):
   ```js
   const srcScale = (sceneNow && sceneNow.srcScale) || 1;
   const natLong  = Math.max(sceneNow.img.naturalWidth, sceneNow.img.naturalHeight);
   const oldLong  = Math.min(LONG, Math.max(SCENE_MIN_LONG, Math.round(natLong / srcScale / SCENE_HEADROOM)));   // 예전 원본이었다면 나왔을 크기
   const longSide = srcScale > 1
     ? (({ '16:9': 1920, '9:16': 1920 })[state.ratio] || 1568)      // 비율별로 필요한 만큼만(1:1 을 1920 으로 뽑으면 합성 캔버스가 3840² 라 휴대폰에 무겁다)
     : Math.min(LONG, Math.max(SCENE_MIN_LONG, Math.round(natLong / SCENE_HEADROOM)));
   // 구도 유지 — 예전 원본·예전 출력일 때와 같은 '카메라 당김 한도'가 되게 한다
   const keepZoom = longSide / (oldLong * srcScale);                // srcScale 1 이면 정확히 1
   ```
   그리고 `composeScene` 호출의 `maxSrcScale: 1.15*SS` 를 `1.15*SS*keepZoom` 으로. 근거: scene.js 의 한도는 `zoomCap = maxSrc / base`(`base` = 합성 폭 / 사진 폭)이므로, 이 곱을 넣으면 `zoomCap` 이 예전 값(1.15 × 1254 / 1080 ≈ 1.335)과 같아진다. 작은 작품용 1.25배 · 사용자 확대용 1.25배는 그 값에 곱해지므로 함께 유지된다.
   - 벽 배경(`srcScale` 없음)은 `keepZoom = 1` 이고 계산식도 그대로라 **픽셀까지 그대로**여야 한다.
4. 벽 명암 · 벽 진정은 고칠 게 없다 — 둘 다 사진 크기에 비례한다(`autoLod = log2(긴 변 / 11)` 은 2508px 에서 7.8 로 상한 9 안, `wallCalm` 의 흐림 반경은 합성 캔버스의 0.4%). 그래도 `scratchpad/vt/leak.mjs` + `leak.py` 로 실내 7장의 전/후를 **재서 확인**한다. `calmtune.py --write` 는 쓰지 말 것(다른 벽까지 덮어쓴다 — 규칙 75).
5. 결과: 1:1 1568² · 4:5 1254×1568 · 3:4 1176×1568 · 16:9 1920×1080 · 9:16 1080×1920.

**함정**

- `SUPERSAMPLE` 2.0 · `STAGE_MAX` 4096 — 1920 이면 합성 캔버스가 3840 이라 한도 안이다. 한도를 넘는 값으로 올리지 말 것.
- 리뷰 때의 '고친 뒤'는 사진을 2.45배로 바꿔 받아 뽑았다(`UP=2.45 node after.mjs res`) — 저장본 크기는 같지만 그때는 당김 한도를 안 묶어 **가구가 잘렸다**. 이번 구현의 구도는 그 그림이 아니라 지금 구도다.
- 기본 배경(갤러리 살롱)을 처음 받는 양이 190KB → 700KB 안팎이 된다. `scratchpad/artlook-ux/walk.js` 의 ② '받는 것'과 e2e `69` 의 무게 확인이 숫자를 들고 있으면 새 값으로 고친다(**벽 사진을 1장만 받는다**는 판정은 그대로여야 한다).
- **배경 자체가 또렷해지는 건 아니다.** 또렷해지는 건 액자와 작품이다. 더 큰 원본을 받으면 파일을 바꾸고 `srcScale` 를 지운다.
- 구도를 바꾸는 일(실내에서 작품을 더 크게)은 **이 묶음에서 하지 않는다**. 리뷰 때 한도를 풀어 봤더니 작품은 33% → 45% 로 커졌지만 가구가 잘렸다. 하려면 따로 사용자에게 물을 것.

### WP4 — 화면 틀

#### A. 휴대폰 편집 전용 화면

1. **판정** — `lib/siteMode.ts` 에 `isArtLookEditor(pathname, search)`(= `/mypage` 이고 `tab=artlook`). `Layout` 은 이 값과 `useMediaQuery('(min-width: 1024px)')` 로 `bare = 편집 화면 && 1024px 미만` 을 구한다. `bare` 면 `Navbar` · `BottomTabBar` · 푸터 · 하단 여백(`pb`)을 그리지 않는다. 홈페이지 주소에서 쓰는 `site` 분기와 같은 자리다.
   - 훅은 조건부 반환 **위**에(`hooksBeforeReturn.test.ts`).
   - 두 배치를 CSS 로 둘 다 그려 감추지 말 것 — 하나만 그린다.
2. **마이페이지** — `ArtLookSection` 의 제목 줄(`<h2>ArtLook</h2>` + 한 문장)은 `bare` 일 때 `sr-only` 로(지우지 않는다 — e2e `30` 이 화면 이름을 본다). `useFillHeight(boxRef, { min: 340, gap: bare ? 0 : 24 })` — `gap` 을 안 주면 아래에 24px 흰 띠가 남는다. 좌우 여백 · 테두리도 `bare` 에서는 없앤다.
3. **iframe 에 알리기** — 주소에 `&bare=1` 을 붙여 첫 그림부터 맞추고(`lib/artlook.ts` 에 `artLookEmbedUrl(bare)` — `ARTLOOK_EMBED_URL` 을 쓰는 테스트가 있으니 함께 고친다), 창 크기가 경계를 넘으면 `postMessage({ type:'artlook:mode', bare })` 로 알린다. **iframe 의 `key` 에 `bare` 를 넣지 말 것**(다시 뜨면 고르던 것이 날아간다). iframe 쪽은 `<html class="bare">` 를 켜고 끈다. 받는 쪽은 `e.origin === location.origin && e.source === window.parent` 를 확인한다.
4. **iframe 안의 머리** — 지금 `.top`(새 탭 전용, 임베드에선 감춤)을 `.embed.bare` 에서 보이게 한다: [닫기](아이콘 단추, `aria-label="닫기"`) · `ArtLook` · 오른쪽 [저장]. 한 문장(`.sub`)은 감춘다.
   - [닫기] → `postMessage({ type:'artlook:goto', to:'close' })`. `readArtLookMessage` 에 `to:'close'` 를 더하고, `ArtLookSection` 은 `navigate(-1)`(기록이 없으면 `/mypage`).
   - 안드로이드 앱의 뒤로가기는 이전 화면으로 간다(창이 아니므로 `role="dialog"` 를 달지 않는다).
5. **[저장]의 자리** — `#dl` 은 한 벌만. 좁은 칸 + `bare` 에서는 `.actions` 를 머리 오른쪽에 고정한다(`position:fixed; top:calc(env(safe-area-inset-top) + 4px); right:8px` · 테두리 · 여백 없음), `#toStory` 는 저장 창으로 간다(C). 넓은 칸(`min-width:860px` 블록)에서는 `position:static` 으로 되돌린다 — 아이패드 가로처럼 `bare` 인데 넓은 칸인 경우가 있다.
6. **칩 칸 높이** — `--pane-h` 144px → **176px**(액자 탭이 세 줄: 모양 44 · 재질 60 · 매트 44). 아이폰 13 에서 머리 52 + 탭 44 + 칩 칸 176 = 272 → 미리보기 392px(폭 390 이라 390 정사각). 아이폰 SE(320×568)는 296px.
   - `bare` 가 아닌 좁은 칸(1024px 노트북의 탭 안)도 같은 176 을 쓴다. `walk.js` 의 pc1024 미리보기 하한(260)을 지키는지 볼 것. 못 지키면 `bare` 일 때만 176.

- 모양을 바꾸면 **같은 재질을 유지**한다. 없으면 가까운 것으로: 골드 → 샴페인 → 오크, 메이플 → 오크, 샴페인 → 오크, 실버 → 화이트, 아이보리 → 화이트, 그 밖에는 그 모양의 첫 재질.
- `selectFrame(i)` 를 코드로 부르면(기억 · 추천 조합) 모양 줄도 따라 맞춘다.
- 재질 칩은 지금 칩과 같은 `.chip.frame[data-id]`(누르면 `selectFrame`). 그래야 기존 테스트 · 하니스의 선택자가 산다. 다만 그 칩이 **지금 모양의 것만** DOM 에 있으므로, 테스트 도우미 `pickFrame(frame, id)`(모양을 먼저 누르고 칩을 누른다)를 e2e `lib/helpers.ts` 에 만든다.
- 좁은 칸: 줄 1 모양(글자 단추, 옆으로 민다) · 줄 2 재질(모서리 칩 44px + 이름) · 줄 3 매트(없음 · 좁게 · 넓게 + 색 줄). 넓은 칸: '모양' 4열 격자(모서리 그림 + 이름) → '재질' 격자 → '매트'.
- 캔버스 랩(`none`)이면 매트는 지금처럼 비활성 + 이유.

**모서리 칩** — 칩 그림을 '액자 전체'에서 '왼쪽 위 모서리 확대'로 바꾼다(재질 · 살 폭 · 깊이가 한눈에 갈린다 — 목업의 재질 줄). `build-artlook-thumbs.mjs` 에 더한다:

- 장면 합성으로 굽는다(벽 = 화이트 플라스터 `white-plaster`, 작품 = `dummyArt`, 매트 5%, 캔버스 랩만 0). `window.__artlook.piece` 로 조각 사각형을 받아 **왼쪽 위에서 (−34px, −34px) · 190px 정사각**을 잘라 96px WebP 로(1568px 출력 기준 — 출력 크기가 다르면 비례). 원형은 원의 225° 지점(`cx − r·0.707, cy − r·0.707`) 둘레. `scratchpad/artlook-review/assets.cjs` 의 `fc-*` · `sh-*` 가 같은 방식이다.
- 파일: `frames/corners/<액자 id>.webp`. 모양 칩은 대표 액자의 것을 쓴다(몰딩 oak · 넓은 몰딩 black-wide · 슬림 oak-thin · 플로터 floater-oak · 박스 box-oak · 원형 round-black · 액자 없음 canvas-wrap).
- 예전 `frames/chips/*.webp` 는 쓰는 곳이 없어지면 지운다(`view.js` · 다른 화면이 쓰지 않는지 grep 으로 확인한 뒤). `artlookScreen.test.ts` 의 '칩 파일이 다 있다'를 `corners` 로 바꾼다.
- WP1 이 끝난 뒤에 굽는다(칩에 그림자가 들어간다).

완료 기준: 보이는 액자 28종 전부가 화면에서 두 번 누르기 안에 골라진다 · 모양을 바꿔도 재질이 유지된다 · 저장 파일 이름에 액자 이름이 그대로 · 칩 파일 28개 합 200KB 이하 · **엔진 결과물은 픽셀 차이 0**(이 묶음은 화면만 바꾼다).

`ui.js` 에 `PRESETS`(데이터)와 `applyPreset(p)` · `presetMatches(p)`.

| `cube` | 화이트 큐브 | black | 좁게 · 흰색 | white-cube | 0 |
| `living` | 따뜻한 거실 | oak | 좁게 · 미색 | gallery-living | 0 |

- 칩 그림은 **미리 구운 파일** `presets/<id>.webp`(184px, `build-artlook-thumbs.mjs` 가 데모 그림 `/demo-art/dawn-window.jpg` 로 굽는다). ⚠️ 내 작품으로 여덟 조합을 그 자리에서 그리지 말 것 — 배경 여덟 장(장당 1MB 안팎)과 액자 사진을 다 받게 된다("고른 것만 받는다"가 깨진다).

- 조합의 id 가 없는 장면 · 액자를 가리키면(목록에서 빠짐) 그 칩을 그리지 않는다.

완료 기준: 조합 하나를 누르면 그리기 1번 · 새로 받는 것은 그 배경 1장 + 그 액자 자산뿐 · 새로고침 뒤 유지.

### WP7 — 작품 크기 칩

**왜** — 치수가 없는 작품이 대부분이고(10월 조사 83%), 지금은 [크기 입력하기]가 홈페이지 편집 화면으로 나가는 링크뿐이다.

- 작품 탭, 한 점 모드, **`sizeText` 가 없는 작품**에서만 줄을 보인다: `크기` + [10호][20호][30호][50호][100호][직접 입력].
- 호수 → 긴 변(cm): 10호 53.0 · 20호 72.7 · 30호 90.9 · 50호 116.8 · 100호 162.2. **긴 변만 정하고 짧은 변은 사진 비율로** 만든다(F · P · M 형을 고르게 하지 않는다). 세로 그림이면 `세로 = 긴 변`. 만든 문자열은 저장소 관례대로 **`세로 × 가로 cm`**(규칙 54 — 순서를 뒤집으면 비율이 거꾸로 걸린다).
- 고른 값은 `localStorage` `artlook:sizes` 에 작품 주소별로(원 맞추기 `artlook:circles` 와 같은 방식). 그 작품을 그릴 때 **작품 객체의 사본**에 `sizeText` 를 얹어 `selectedWork` 로 넘긴다(넘겨받은 목록은 고치지 않는다). 여러 점 모드에서도 같은 값을 쓴다.
- 서버에서 진짜 크기가 오면 그게 이긴다(기억한 값은 무시).
- 처음엔 아무 칩도 눌려 있지 않다(지금처럼 높이 90cm 가정). 줄의 안내 글 '크기를 적지 않아 높이 90cm(30호 정도)로 걸었어요' 와 [크기 입력하기] 는 그대로 — e2e `69` E 가 본다.
- [직접 입력]: 작은 창(`role="dialog"`)에 세로 · 가로(cm, `inputmode="decimal"`, 1~1000).
- 로그아웃하면 `artlook:works` 를 지우는 곳(`lib/artlook.ts`)에서 `artlook:sizes` 도 지운다.
- 데모 작품(크기가 다 있다)에는 줄이 안 뜬다.

완료 기준: 30호 → 100호 를 누르면 `window.__artlook.piece` 가 커진다 · 새로고침 뒤 유지 · 크기가 있는 작품에는 줄이 없다 · 그리기는 누를 때마다 1번.

### WP8 — 배경 [공간 | 벽] · 마무리 탭

- **배경(좁은 칸)**: 칩 줄 위에 [공간][벽] 두 단추. 고른 무리의 칩만 보인다(칩에 `data-group`, 안 고른 쪽은 `hidden`). 처음엔 **지금 고른 배경이 속한 무리**. `state.sceneIdx` 는 전체 목록 번호 그대로(규칙 44j — 걸러진 목록의 번호로 바꾸지 말 것). 넓은 칸은 지금처럼 두 무리를 제목과 함께 다 보인다(두 단추는 CSS 로 감춘다).
  - ⚠️ 10-04 에는 이 토글이 "미리보기 높이를 먹는다"고 뺐다. 편집 전용 화면으로 164px 이 생겨 되살리는 것이다 — 규칙 65 의 그 문장을 고칠 것.
- **마무리**: 비율(`#ratios`) · 조명(`#lightOp`) · **벽 캡션 스위치**(`role="switch"`, 배경 탭의 [벽 캡션 붙이기] 단추를 옮긴다). 붙일 수 없을 때(여러 점 · 적을 정보가 없음 · 액자가 박힌 장면)는 스위치를 끄고 못 누르게. 배경 탭의 줄(`#sceneNote`)에는 배경 이름과 크기 안내만 남긴다.
- 캡션을 켰는데 자리가 없어 못 붙인 안내는 스위치 옆에.

### WP9 — (선택) 액자 재질 늘리기: 가진 사진에서 색만 옮긴다

**사용자가 색을 고른 뒤에만.** 시안은 캔버스의 '액자 재질 늘리기 시안'(도장 8색 · 나무 4색), 만드는 법은 `scratchpad/artlook-review/recolor-frames.mjs` 의 `recolor()`.

- 원리: 액자 사진의 불투명 픽셀을 OKLab 으로 옮겨 **평균만 목표 색으로**, 밝기 · 색의 편차(결 · 명암 · 이음매)는 그대로 더한다. 벽 3종을 그렇게 만든 전례가 있다(규칙 75). **목표와 밝기가 비슷한 사진에서 옮길 것** — 어두운 색은 블랙에서, 밝은 색은 화이트에서, 나무 색은 오크 · 월넛에서.
- 구현은 **파일을 늘리지 않고 엔진이 받을 때 옮기는 쪽**을 권한다: `FRAMES` 맨 뒤에 `{ id:'navy', name:'네이비', kind:'photo', photo:'black', tint:'#1f2c47', rail:0.052 }` 처럼 적고, 사진 액자를 로드 때 한 번 굽는 자리(`FRAME_GRADE` 를 입히는 곳 — `ensurePhotoFrame` 이 부르는 굽기)에서 `tint` 가 있으면 색을 옮긴 캔버스를 `photo@tint` 열쇠로 따로 보관한다. 그러면 사진 파일은 원본 하나를 나눠 쓴다(1MB 짜리 PNG 를 색마다 더하지 않는다).
  - 색 옮기기는 `FRAME_GRADE` 보다 **먼저**. 나무 색은 원본의 보정(오크 [0.45,0.93])을 그대로 타면 탁해진다 — 항목에 `grade:[…]` 를 따로 줄 수 있게 한다.
  - 자산을 재는 값(`measureAssetLight` · `assetFaceEnd` · `faceRGB`)은 **옮긴 뒤의 캔버스**로 잰다.
  - 1백만 픽셀 한 번(수십 ms)이다. 고를 때 한 번만 하고 보관할 것.
- 모양 표(WP5)에 재질로 더하고 모서리 칩을 굽는다. `docs/artlook-asset-provenance.md` 에 "자체 제작 — <원본> 사진에서 색만 옮김" 을 적는다.
- 완료 기준: 기존 액자 28종 픽셀 차이 0 · 새 액자마다 `scratchpad/vt/nomat.mjs` 통과 · 300px 로 줄였을 때 서로 구분되는지 시트로 사용자 확인.

### 3.3 눈으로 볼 것 (숫자로 안 잡히는 것 — 캡처를 보고에 붙인다)

- 줄인 그림(300px)에서 액자 네 귀퉁이에 얼룩이 보이는가.
- 실내 배경에서 액자만 지나치게 쨍해 떠 보이지 않는가(배경은 그대로 무르다).
- 모서리 칩으로 블랙 5종이 서로 갈리는가(살 폭 · 깊이).
- 휴대폰에서 탭마다 칩 칸 아래가 잘리지 않는가(크롬 · 사파리 엔진 둘 다).
- 추천 칩 여덟 장이 서로 달라 보이는가.

### 3.4 사용자에게 보일 순서

4. 보고는 전/후 표 + 시트. 못 본 것(실기기)은 못 봤다고 적는다.

## 4. 순서와 의존

```
WP0 → WP1 ─┐
      WP2 ─┼→ (칩 굽기는 WP1 뒤) → WP5 → WP6
      WP3 ─┘
WP0 → WP4 → WP5 · WP7 · WP8 → WP10
WP9 는 사용자가 색을 고른 뒤, WP5 다음에
```

- 엔진 묶음(WP1~3)과 화면 묶음(WP4~8)은 서로 독립이다. 화면 묶음을 먼저 해도 된다 — 다만 **칩은 WP1 이 확정된 뒤에** 굽는다(다시 굽지 않게).
- 묶음마다 ③을 돌리고 다음으로 넘어간다. 한꺼번에 고치고 한꺼번에 검증하지 말 것 — 화면만 바꾼 묶음에서 결과물이 달라지면 어디서 달라졌는지 못 찾는다.

## 5. 위험

| 위험 | 대비 |
|---|---|
| 그림자를 사용자가 마음에 들어 하지 않는다 | WP1 은 `scene.js` 두 군데뿐이다. G1 에서 되돌리면 끝 |
| 실내 사진이 커져 휴대폰에서 무겁다 | 사진은 지금 벽 배경과 같은 2508px, 출력도 비율별로 묶었다(1:1 은 벽과 같은 1568). 받는 양은 장당 900KB 상한. 그래도 9:16(합성 2160×3840)이 느린 기기가 있으면 9:16 · 16:9 의 긴 변을 1568 로 낮춘다 |
| 벽 무늬가 작품에 더 비친다 | WP2-4 의 `leak.mjs` 로 잰다 |
| 편집 전용 화면에서 나갈 길이 없다 | [닫기] + 브라우저 · 앱 뒤로가기. e2e `84` A |
| 옛 화면을 캐시로 들고 있는 사람 | `ui.js?v=빌드` · 고정 이름 파일은 no-cache(규칙 65). 새 칩 폴더도 `artlook/` 아래라 미리받기에 안 들어간다 |
| 기억해 둔 선택(`artlook:prefs`)이 새 화면과 안 맞는다 | 액자 id · 장면 id · 비율은 그대로다. 숨긴 액자는 지금처럼 `alias` 로 연다 |
| 테스트가 옛 탭 id 를 본다 | WP10 의 목록대로 고친다. 가드를 지우지 말고 새 구조로 옮긴다 |

## 6. 덧붙임 — 액자 사진을 더 구하는 길 (사용자 결정 사항, 이 계획의 범위 밖)

"28종이 작게 보면 8종"의 절반은 화면 문제(WP5 — 모양 × 재질 · 모서리 칩)이고, 나머지 절반은 **서로 다른 재질이 부족한 것**이다. 2026-11-17 에 사용자에게 제안한 길:

| 길 | 상태 | 비고 |
|---|---|---|
| ① 가진 사진에서 색만 옮기기 | **시험함** — 도장 8색 · 나무 4색 시안이 캔버스에 있다. 100% 로 봐도 결 · 이음매 · 명암이 남는다 | WP9. 새 사진이 필요 없다. 모양(살 폭 · 깊이)은 늘지 않는다 |
